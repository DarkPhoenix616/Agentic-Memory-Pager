Executive Summary

Modern AI coding agents (Claude Code, Cursor, Aider) suffer from two critical failure modes when working sessions grow long:

  • Context Rot — When the active context window fills up, agents perform lossy compaction, summarising the chat into a paragraph and permanently discarding the raw logs.
  • State Amnesia — Early architectural decisions, exact variable names, and reasoning chains are silently lost, causing the agent to contradict its own earlier work.

The Agentic Memory Pager (AMP) solves this by introducing Virtual Memory Paging for LLMs — the same concept that operating systems use to handle RAM overflow by paging data to disk:

Short-Term Memory (RAM) = Active LLM Context Window
Long-Term Storage (Disk) = External Vector Database (ChromaDB)
Page-Out = Compaction + Storage  |  Page-In = Semantic Retrieval

AMP uses a Dual Compaction Engine: AST-aware parsing for source code and Recursive Language Models (RLMs) for conversational history. Both engines produce structured, validated data that conforms to the Pydantic schemas defined in harness/guardrails.py.

Technology Stack & Design Choices

LayerTechnologyOwnerWhy This Choice
ProtocolFastMCPT1 Native Python MCP server. Exposes tools as JSON-RPC endpoints compatible with any MCP client (Claude, Cursor).
OrchestrationLangGraph + LiteLLMT4 LangGraph provides typed, stateful graph execution. LiteLLM gives model-agnostic inference routing with a single API.
Code Parsingtree-sitter / astT2 AST parsing is the only lossless way to extract structure from code. Tree-sitter supports 40+ languages; Python's built-in ast is a fallback.
Local InferenceOllama (Llama-3, Phi-3)T3 Self-hosted inference means zero API cost and full data privacy. Phi-3-Mini is fast for summarization; Llama-3-8B is more capable.
Vector StorageChromaDBT1 Embedded, file-based vector database. No infrastructure required. Supports metadata filtering alongside semantic search.
Relational StorageSQLiteT1 Stores structured metadata (session IDs, timestamps, token counts) for fast non-semantic queries. Ships with Python.
GuardrailsInstructor + PydanticT4 Instructor patches LLM outputs through Pydantic models, guaranteeing that every compacted payload conforms to the schema before DB write.
ObservabilityLangfuse / StreamlitT4 Langfuse traces every LLM call. Streamlit provides a live dashboard showing token counts and memory page-ins.
Key Constraint: The entire system must run locally with no paid APIs. All inference uses Ollama. All storage is file-based (ChromaDB + SQLite). This keeps the project self-contained, free, and offline-capable.

Pydantic Data Schemas — Full Reference

All schemas live in harness/guardrails.py. This is the single source of truth for inter-module data exchange. Every module imports from this file — never pass raw dictionaries between teammates' components.

Model 1

CodeSymbol

Used by: T2 → T4

A single structural unit extracted from a source file — one function, one class, one method, or a module-level variable. Storing symbols individually allows retrieval of a specific function without fetching the entire file.

FieldTypeRequiredExplanation
namestrYesThe identifier name, e.g., "calculate_tokens"
typeLiteral["class","function","method","variable"]YesWhat kind of construct this symbol is
signaturestrYesFull signature with type hints: "def foo(x: int) -> str:"
docstringOptional[str]NoPreserved docstring from source, if present. Defaults to None.
start_lineint (≥1)Yes1-indexed line number in the original file — enables traceability back to source
Model 2

CodeMemorySchema

T2 output → T4 wraps in UnifiedMemory → T1 stores

The complete compacted output for an entire source file. A 5,000-token file is reduced to ~500 tokens by keeping only the structural skeleton: imports, class hierarchy, function signatures, and docstrings. Function bodies are stripped.

FieldTypeRequiredExplanation
file_pathstrYesRelative path to the parsed file, e.g., "harness/token_monitor.py"
languagestrYesProgramming language — e.g., "python". Needed so tree-sitter loads the correct grammar.
importsList[str]NoAll import/require statements, verbatim. Defaults to [].
symbolsList[CodeSymbol]NoAll extracted structural symbols. Defaults to [].
dependenciesList[str]NoCross-file or external module dependencies. Defaults to [].
summaryOptional[str]NoAI-generated one-paragraph description of the file's role and responsibilities.
original_token_countint (≥0)YesToken count before compaction — used to compute compression ratio.
Model 3

TextMemorySchema

T3 output → T4 wraps in UnifiedMemory → T1 stores

The compacted output for a single chunk of conversation history. Instead of keeping 50,000+ tokens of raw dialogue, the RLM engine distills each chunk into a structured fact map containing only semantically important information. Supports multi-pass compaction via chunk_index / total_chunks.

FieldTypeRequiredExplanation
chunk_indexint (≥0)Yes0-indexed position of this chunk in the current compaction pass. Must be < total_chunks.
total_chunksint (≥1)YesTotal chunks in this pass. E.g., if a conversation is split into 3 parts, total_chunks = 3.
timeframestrYesHuman-readable window, e.g., "Session 0 to 80% token limit, messages 1-247"
architectural_decisionsList[str]NoKey design choices made in this context window. E.g., "Use ChromaDB not Pinecone".
bugs_resolvedList[str]NoIssues identified and fixed in this chunk.
user_constraintsList[str]NoExplicit rules or preferences the user stated. E.g., "No paid APIs".
factual_summarystrYesDense prose paragraph of everything in this chunk — the primary field used for semantic retrieval.
original_token_countint (≥0)YesToken count of the raw dialogue chunk before summarization.
Validation Rule: A model_validator enforces that chunk_index < total_chunks. Violating this raises a ValidationError.
Model 4

UnifiedMemory

T4 creates → T1 stores & retrieves

The universal envelope that is persisted to ChromaDB and SQLite. Wraps either a CodeMemorySchema or TextMemorySchema with consistent metadata. T1's MCP tools only deal in this type — the storage layer is completely agnostic to content type.

FieldTypeRequiredExplanation
idstr (UUID4)AutoAuto-generated UUID4. Unique identifier for this memory object.
timestampdatetime (UTC)AutoAuto-generated UTC timestamp of creation.
session_idstrYesLinks this memory to the current agent session.
memory_typeLiteral["code","text"]YesIndicates which payload is populated.
compaction_sourceLiteral["ast","rlm"]YesWhich engine produced the payload. Must be consistent with memory_type.
code_payloadOptional[CodeMemorySchema]ConditionalRequired when memory_type == "code". Otherwise None.
text_payloadOptional[TextMemorySchema]ConditionalRequired when memory_type == "text". Otherwise None.
raw_token_countint (≥0)YesTokens consumed by the original pre-compaction content.
vector_embedding_idOptional[str]Post-writeChromaDB doc ID. Starts as None, set by T1's store_memory() after writing.
Cross-field Validation: A model_validator enforces consistency:
memory_type="code" requires compaction_source="ast" and code_payload set.
memory_type="text" requires compaction_source="rlm" and text_payload set.
Model 5

TokenState

T4 internal — LangGraph state object

The live state object that flows through every node of the LangGraph state machine. Not persisted — lives in memory for the duration of a session. Carries all information needed to decide: should we compact? What do we compact? This is T4's central nervous system.

FieldTypeDefaultExplanation
session_idstr—Current session ID. Matches session_id in stored UnifiedMemory records.
current_token_countint (≥0)0Live count of tokens in the active context window.
token_limitint (≥1)—Model's max context window size, e.g., 128000 for Llama-3.
compaction_thresholdfloat (0–1]0.80Fraction of token_limit at which compaction fires. Configurable per session.
context_chunksList[dict][]Raw message dicts in the active window. Each has role, content, type fields.
oldest_chunk_typeLiteral["code","text"]"text"Content type of oldest chunk — drives routing to AST or RLM compactor.
compaction_in_progressboolFalseGuard flag preventing re-entrant compaction. Set True when compaction begins.
total_compactionsint (≥0)0Telemetry counter — how many compaction cycles have completed this session.

Computed Properties

PropertyReturnsLogic
utilizationfloatcurrent_token_count / token_limit — context window fill percentage
should_compactboolutilization >= compaction_threshold AND NOT compaction_in_progress

MCP Tool Catalogue

These are the FastMCP tools exposed by Teammate 1's server (server/mcp_server.py). Any MCP client (Claude, Cursor, custom agent) can call these. All tools use the Pydantic schemas from harness/guardrails.py as their input and output types.

store_memory MCP TOOL
InputUnifiedMemory + session_id: str
Outputstr — The assigned id (UUID) of the stored memory
DescriptionSaves a validated UnifiedMemory object to ChromaDB (vector embedding of factual_summary or summary) and SQLite (full JSON metadata). Sets vector_embedding_id on the object after writing.
search_vault MCP TOOL
Inputquery: str, session_id: str, top_k: int = 5
OutputList[UnifiedMemory]
DescriptionSemantic similarity search across all stored memories for the given session. Embeds the query, queries ChromaDB, and returns the top-k most relevant UnifiedMemory objects. Used by the agent to "page in" relevant past context.
page_context MCP TOOL
Inputsession_id: str, limit: int = 10
OutputList[UnifiedMemory]
DescriptionPages the most recent N memory objects back into the active context, ordered by timestamp descending. Used when resuming a session to reload recent memories without semantic search.
get_token_state MCP TOOL
Inputsession_id: str
OutputTokenState
DescriptionReturns the current live TokenState for a session. Used by the Streamlit dashboard to display real-time token utilization and compaction statistics.
list_sessions MCP TOOL
Inputnone
OutputList[str] — all session IDs in the database
DescriptionReturns all active session IDs stored in SQLite. Used for dashboard session selection and debugging.
delete_memory MCP TOOL
Inputmemory_id: str (UUID of the target memory)
Outputbool — True if deletion succeeded
DescriptionDeletes a specific UnifiedMemory object from both ChromaDB and SQLite atomically. Used for memory pruning or cleanup.

End-to-End Data Flow

The following shows the complete lifecycle of one compaction event, from trigger to storage:

1
Token Monitor fires
TokenState.should_compact returns True because current_token_count / token_limit ≥ 0.80. The LangGraph conditional edge routes to the compaction node. compaction_in_progress is set to True.
↓
2
Dynamic Router decides
Inspects TokenState.oldest_chunk_type. If "code" → calls T2's AST Compactor. If "text" → calls T3's RLM Compactor.
↓
3
Compactor produces schema
T2 returns a CodeMemorySchema object. T3 returns a TextMemorySchema object. Both are Pydantic-validated at the point of creation.
↓
4
Instructor validates via guardrails
T4 uses Instructor to patch the LLM output through the Pydantic schema a second time, guaranteeing structured conformance before DB write. Any invalid output is retried.
↓
5
UnifiedMemory envelope created
T4 wraps the validated payload in a UnifiedMemory object with auto-generated id and timestamp. The cross-field validator ensures memory_type, compaction_source, and payload fields are consistent.
↓
6
FastMCP store_memory() called
T1 receives the UnifiedMemory envelope, embeds the summary text into ChromaDB, saves the full JSON to SQLite, sets vector_embedding_id, and returns the memory's id.
↓
7
Context window cleared
The raw context chunks are removed from the active window, freeing the tokens. TokenState.compaction_in_progress is reset to False and total_compactions is incremented.
